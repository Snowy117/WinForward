# Research: SOCKS5 Control + Capture/Dispatch Front-End Review (2026-08-30)

- **Query**: Read-only performance/stability review of the SOCKS5 control connection and the capture → dispatch → action front-end.
- **Scope**: full read of `Socks5ControlConnection.cs`, `Socks5State.cs`, `Capture/*`, `FlowDispatcher.cs`, `PacketFlowClassifier.cs`, `SelfTrafficRegistry.cs`, `IdleExpirySweeper.cs`, `NdisApi/*` (capture, pools, driver, ABI), `PacketRuntime.cs`; skim of `PacketChecksums.cs`.
- **Date**: 2026-08-30, baseline commit `e5667af`.
- **Excluded (already landed)**: ETH_M_REQUEST batched reads (cap 32, in-order), ArrayPool frame lease returned in `ProcessAsync` finally, in-place TCP rewrite, Proxy joined dispatcher warm entry (bench shape), C2 IPAddressValue cold-edge storage, C1 indexed MAC swap, vectorized (16×) + incremental (18.7×) checksums, adapter local-address cache (change-event + TTL).

## A) Architecture Summary

**Packet → capture → dispatch → action:**
1. **Capture**: `MultiAdapterCaptureLoop` runs one `NdisCapturePump` per adapter (`NdisCapture.cs:31`). Each iteration: `NdisApiDriver.TryReadPackets` (one `GetAdapterPacketQueueSize` IOCTL + one stack-allocated `ETH_M_REQUEST`-based `ReadPackets` batch IOCTL under the per-adapter native gate, up to 32 slots) → strictly in-order awaits per slot `CapturePacketProcessor.ProcessAsync` (batch-slot contract: no slot reuse while the handler is in flight).
2. **Parse/classify**: `IPTcpUdpPacket.TryParse` runs directly over the native span; `PacketLease.TakeNative` defers materialization (ArrayPool rent+copy only on first `.Frame` access).
3. **Dispatch**: `FlowDispatcher.DispatchAsync` intends a non-async warm entry for resolved flows; everything else enters `DispatchSlowAsync` (self-traffic check → TCP reverse handler → flow-table resolve/claim → process attribution → decision execution).
4. **Action**: `NdisPacketActionExecutor` — Pass re-injects the native capture buffer in place via `PrepareForReinjection` (pooled copy if materialized), Block consumes the frame, Proxy routes TCP to `TcpProxyCoordinator` (SYN → listener alloc → DNAT rewrite → inject; mid-flow data rewrite → inject; reverse-leg rewrite → inject; the accept loop spawns the SOCKS5 relay) and UDP to `UdpProxyCoordinator` (per-flow background session setup with bounded drop-oldest queue; inline sends on ready sessions via non-blocking `SendTo`; responses rebuilt by `UdpResponseReinjector` into pooled native buffers).
5. **SOCKS5 control** (`Socks5ControlConnection.cs`): DNS resolve (30s cap) → one attempt per candidate address, 30s per-attempt × up to 4, self-traffic registered after `Bind` before SYN → greeting/method (optional user/pass) → command (CONNECT/UDP ASSOCIATE) → exact-size prefix (5B) + full reply reads with discriminating parser (L2), BND normalization (M1/M2). The 30s attempt budget extends through the command stage; the relay takes over the stream with unlimited socket timeouts (R1).

## B) Performance Findings

### B.1 Remaining per-packet clones (the "phase 2" item)

**B.1.1 — TCP proxy data path: two full frame copies per packet. (HIGH)**
- Materialization #1: `TcpProxyCoordinator.HandlePacketAsync` calls `ClassifyTcpSyn` on `packet.Lease.Frame.Span` (`TcpProxyCoordinator.cs:297`) — the first `.Frame` access triggers `PacketLease.Materialize` (`PacketRuntime.cs:74-83`): `ArrayPool.Rent` + full ~1514B native→managed copy. Same in `ReinjectExistingFlowDataAsync` (line 152) and `HandleReverseAsync` (line 204).
- Copy #2: `TcpRedirectInjector.InjectAsync` (`TcpRedirectInjector.cs:12-24`) rents a pooled `NdisPacketBuffer` and `SetFrame`s the entire frame back into native memory, then one IOCTL.
- The forcing reason is `TryGetWritableFrame` (`TcpFrameRewriter.cs:37-43`): `MemoryMarshal.TryGetArray` requires a managed array. But `PacketChecksums.TryRewriteTcpEndpoints` and `ClassifyTcpSyn` both take `Span<byte>`, and `NdisPacketBuffer.GetFrame()` (`NdisPacketBuffer.cs:71-76`) returns a *writable* native span — and the pump contract guarantees slot stability for the whole dispatch.
- **Fix**: when `!packet.Lease.IsMaterialized && packet.NativeFrame.Buffer is { } b`, parse/rewrite directly on `b.GetFrame()`, then add a `RetagForReinjection(adapterHandle, deviceFlags)` API (mirroring `CompleteFrame`, `NdisPacketBuffer.cs:96-105` — length unchanged, only direction retag) and inject via the existing single-packet send. `PassAsync` (`NdisPacketActionExecutor.cs:44-53`) already proves the pattern. The `NotRelevant`→Pass fallback (executor line 107) stops paying 2 copies too. Remaining real copies: UDP setup queue (`BoundedSetupQueue.TryEnqueue` `frame.ToArray()`, `PacketRuntime.cs:173` — bounded, cold) and UDP response frame building (inherent, already into a pooled native buffer, `UdpResponseReinjector.cs:91-128`).
- **Impact**: removes 2×~1.4KB memcpy + ArrayPool/NdisPool traffic per relayed TCP packet; eliminates the only non-IO work per mid-flow packet.

**B.1.2 — UDP proxy: materialization just to parse. (MED)**
- `NdisPacketActionExecutor.HandleUdpProxyAsync` line 134: `IPUdpPacket.TryParse(packet.Lease.Frame, ...)` materializes the whole frame only to read the payload. On a ready session the payload is synchronously encoded into the transport's `_sendBuffer` (`Socks5UdpTransport.cs:210-217`) and dispatch returns — a native span works equally well.
- **Fix**: parse over `packet.InspectionSpan`; pass the payload span into the codec; materialize only when buffering (the setup queue already copies). 1.4M DNS pps = 1.4M full-frame copies saved per second.

### B.2 Dispatch path

**B.2.1 — The production hot entry is dead code. (HIGH — and silent)**
- `FlowDispatcher.cs:129`: `if (_logger.IsEnabled(Trace) || _reverseHandler is not null) return DispatchSlowAsync(...)`. `Program.cs:271` **always** wires `reverseHandler: tcpCoordinator.HandleReverseIfApplicableAsync` in the production `run` composition. Therefore every packet — Pass, Block, Proxy, UDP, TCP — runs the full async slow path; the optimized non-async shape (lines 131-153, "352B→160B") never executes outside benchmark-only compositions. The empirical 2.44M pps / 160B per pkt was measured without a reverse handler wired.
- **Fix (incremental)**: gate the diversion to `... && packet.Context.Key.Protocol == TransportProtocol.Tcp` — the reverse handler is TCP-only anyway (line 221, M5/H1). This immediately restores the warm entry for UDP and all Pass/Block traffic. **Fix (full)**: add a lock-free prefilter to the hot path (e.g. a 65536-bit bitmap of redirect-listener ports, atomically swapped on listener alloc/free; or `Volatile.Read` of the active-redirect count, commonly 0) and divert only candidates to the slow path.
- **Spot-check 2026-08-30: confirmed via direct source read of both sites.**

**B.2.2 — Four locks + seven dictionary probes per packet. (MED)**
- `SelfTrafficRegistry.IsOwned` (`SelfTrafficRegistry.cs:25-34`): global `Lock` + up to 4 `Dictionary` probes (key, reverse, wildcard, wildcard-reverse), once per packet at the hot check. Registration is per-flow cold; reads are per-packet hot — a classic COW target. **Fix**: immutable snapshot array (`Volatile.Read`) or a read/write split.
- `FlowTable.TryResolve` (`Domain.cs:183-189 → 279-289`): `Lock` + 2 probes + `DateTimeOffset.UtcNow` + a `Touch` write, once per packet. Contended on multi-adapter hosts (per-adapter pumps + sweeper + background setup tasks). **Fix**: shard by flow hash; make `Touch` an Interlocked tick write inside `FlowState` so resolve can take a read lock, or move to a concurrent table.
- `TcpRedirectTable.IsReverseCandidate` (`TcpRedirectTable.cs:219-222`): `Lock` + probe, paid per TCP packet via the B.2.1 slow path. The bitmap prefilter also removes this.

**B.2.3 — `DispatchNonFlowAsync` is always async. (LOW)** `FlowDispatcher.cs:247-266`: builds an async state machine per non-flow frame (ARP/ND/ICMP) even when tracing is off. The fragment check already uses `InspectionSpan` (line 270) — a non-async warm variant (self-traffic off → fragment-bit test → Pass) is feasible. Matters on ARP-heavy networks only.

**B.2.4 — No remaining boxing in the hot path**: `CapturedFlowPacket`/`FlowContext`/`FlowKey` are structs; `packet with {...}` is a struct copy; the executor's `ValueTask` is returned directly; `PacketLease.TakeNative`/`Release` are thread-static single-slot (`PacketRuntime.cs:27-28, 91-134`). One subtlety: `Release` may run on a non-pump thread when a proxy await resumes on an IOCP thread, leaving the lease in that thread's cache — correctness holds, caches gradually spread across threads (bounded by thread count).

### B.3 Batched action executor
- **No batching exists**: every re-injection is an individual IOCTL — `SendPacketToAdapter`/`SendPacketToMstcp` each acquire the adapter gate and submit one `EthernetRequest` (`NdisApiDriver.cs:185-209`). A pump batch of 32 same-direction Pass packets = 32 kernel crossings + 32 gate leases.
- The ABI **already imports the unused batched sends** `SendPacketsToAdapter`/`SendPacketsToMstcp` (`NdisApiAbi.cs:217-227`); `EthernetMultiRequest` + `BuildMultiRequest` (`NdisApiDriver.cs:138-183`) are reusable shape.
- **Fix**: accumulate (adapter, direction, buffer) Pass dispositions within a pump iteration; flush on an interleaving proxy/block action of a different direction and at iteration end. Same-adapter same-direction sends commute, so per-adapter ordering is preserved. Serialization per gate is kept per the driver contract.
- **Per-batch marshal cost**: already minimal — requests are stack-built (≤125 slots within the 1KB stackalloc budget, `NdisApiDriver.cs:24, 141-144`); slots are raw pointers, zero managed marshaling; `PacketsSuccess` is clamped before trusting (`NdisNativeCallStatus.cs:44`).
- **Pinning**: none — frames live in `NativeMemory.AllocZeroed` `IntermediateBuffer`s (`NdisPacketBuffer.cs:34-39`); no GC pinning, no pinned-buffer GC pressure. Design is correct.
- Minor: `NdisAdapterGateMap.Get` takes a `Lock` for a dictionary probe on every native call (`NdisNativeCallGate.cs:70-82`) — prepopulate at adapter enumeration, or try a lock-free `TryGetValue` first.

### B.4 SOCKS5 control connection
- Reads are exact-size (`ReadExactlyAsync` on byte[2], 5B prefix, then the exact `TryGetReplyLength`-sized body, `Socks5ControlConnection.cs:254, 261, 268, 282`) — good shape, no per-byte reads.
- Per-command allocations (per-flow cold): `Greeting` allocates a fresh byte[3]/[4] per call (`Socks5State.cs:28` — constant, cacheable `static readonly`); `UsernamePassword` 3 arrays (lines 30-43); `Request` + `GetAddressBytes` (lines 45-56); per-reply byte[5] + byte[10/22] + `new IPAddress` (`Socks5ControlConnection.cs:267-282, 290-293`). ~6-8 small allocations per handshake total — negligible for once-per-flow; if flows per second grow into the thousands, static greeting + per-connection reply buffer fields are free wins (LOW impact).
- **Timeout budget**: 30s DNS cap (lines 15, 62) + 30s per attempt × up to 4 attempts (lines 14-15, 59-60) ≈ **worst case ~150s per failed setup chain** (note: earlier task notes said "10s×2" — the code says 30s×4). All of this runs in the background (UDP via `Task.Run` + the 8-wide setup limiter, `UdpProxyCoordinator.cs:26, 129`; the TCP SOCKS connect happens in the accept/relay loop, not inline in the SYN handler), so the pump never stalls — but a black-holed SOCKS5 server holds a session slot and delays the first datagram ~150s before failing closed. A tighter total cap (e.g. 15-30s shared across attempts) would tighten upstream failover.
- No pooling (by design, per flow); header prebuild is limited to the greeting cache — `Request` always carries the per-flow port.

### B.5 GC mode
- **Not configured**: `WinForward.Cli.csproj` sets only `PublishAot`/`InvariantGlobalization`; no `ServerGarbageCollection`/concurrent-GC settings anywhere, no runtimeconfig template — the AOT default = workstation concurrent GC.
- Does it matter? The warm lane is ~10B/pkt, so GC mode barely matters there; the residual allocation pressure is per-flow (measured ~90KB per UDP session, relay buffers, per-datagram allocations, B.6 below). `<ServerGarbageCollection>true</ServerGarbageCollection>` on 8+ cores would reduce pause risk during session-establishment storms. Low effort, low-MED payoff — do it after the per-datagram fixes, not before.

### B.6 Per-datagram allocations (UDP steady state)
- `UdpProxySession.SendAsync` line 115: `destination.Address.ToIPAddress()` (itself allocating an array, `IPAddressValue.cs:97-105`) + `new IPEndPoint(...)` — **2 heap allocations per relayed datagram** for a destination that is fixed per session (`flow.Remote`). `Socks5UdpTransport.SendAsync` then uses it only for header encoding and sends to `RelayEndpoint` (`Socks5UdpTransport.cs:210-217`). **Fix**: cache the `IPEndPoint` once at session creation (or pass an `Endpoint` struct through); ~96B×pps of gen0 churn to zero. Trivial effort.
- `Socks5UdpTransport.ReceiveAsync` line 271: `new IPEndPoint(IPAddress.Any, 0)` per received datagram — 1 allocation per response; cache the template endpoint. Trivial.

## C) Stability Findings

**C.1 — Pump DisposeAsync/RunAsync use-after-free potential. (LOW — ordering-protected today)**
`NdisCapturePump.DisposeAsync` (`NdisCapture.cs:93-98`) sets `_stopped` and calls `ReleaseBatchBuffers()`, freeing native `IntermediateBuffer`s while `RunAsync` may still be mid-iteration: no coupling between the `Volatile.Read(_stopped)` check (line 68) and batch processing (lines 77-84), and the `Interlocked` guard (line 102) only makes the free happen exactly once — it does not check that the run loop has exited. `TransactionalCaptureRuntime.StopAsync` (`CaptureLifecycle.cs:107-111`) awaits `_runTask` before `CleanupAsync`→`DisposeCaptureAsync` (lines 136-156, 180-181), so in practice the ordering is safe; the type itself permits it. **Fix**: have `DisposeAsync` await an in-flight iteration via a per-pump completion `TaskCompletionSource`, or document it as a class-level contract + debug assert.

**C.2 — Driver error = immediate global fail-closed, no transient retry. (MED)**
`TryReadPackets` throws `Win32Exception` on any queue-probe/read failure (`NdisApiDriver.cs:124-133`, `NdisNativeCallStatus.cs:22-45`); the exception propagates `NdisCapturePump.RunAsync` → `MultiAdapterCaptureLoop` cancels siblings → `TransactionalCaptureRuntime` restores adapter modes → process exits (`Program.cs:223-227`). Transient errors expected during adapter removal, power transitions, or driver pauses kill interception for all adapters. **Fix**: classify errors as retryable vs fatal; bounded backoff + per-adapter pump restart (modes restored/re-applied), global fail-closed only on repeated fatal errors.

**C.3 — Backpressure is delegated to the driver; TCP SYN setup is a per-adapter head-of-line block. (MED)**
No userspace queue bounds/drop policy: the pump pulls as fast as it can, awaiting handlers in order; slow dispatch overflows the driver's in-kernel adapter queue, which silently drops. The hot-path shape is fast; the exposed slow step is `HandleSynAsync` → `TcpRedirectSetup.SetupNewRedirectAsync`, which **allocates and binds a listener socket inline on the pump thread** (`TcpRedirectSetup.cs:59-75`) — port-exhaustion/slow-bind under listener-allocation pressure stalls the entire adapter batch. UDP setup is correctly offloaded (patient admission, `UdpProxyCoordinator.cs:26-27, 280, 129`). **Fix**: move listener allocation off the pump (a pre-allocated listener pool or a setup worker), keeping only rewrite+inject inline.

**C.4 — In-place Pass reinjection relies on two unasserted invariants. (LOW, documented in-file)**
(a) The dispatcher completes the lease *before* the executor runs (`FlowDispatcher.cs:144, 150`) — if leases ever carried an `onCompleted` array-pool return, completion would expose that array to executor reuse; `CapturePacketProcessor.cs:36-41` documents this, and native leases have no callback, so it is currently safe. (b) The batch-slot contract (`PumpDoesNotReuseBatchSlotWhileHandlerIsInFlight` test, archived report). Both are correct but implicit — keep them pinned in `.trellis/spec/backend/hot-path.md`, ideally guarded by a debug-mode lease assertion.

**C.5 — Pool lifetimes. (LOW)**
`NdisPacketBuffer.Dispose` CAS ensures exactly-once return (`NdisPacketBuffer.cs:139-151`); double return is a no-op. `NdisPacketBufferPool.OnReturned` (`NdisPacketBufferPool.cs:70-78`) may marginally exceed capacity under two concurrent returns, and a return racing `Dispose` may land in the queue after teardown until process exit — documented, bounded, benign. The `Rent` loop correctly skips never-marked-rented buffers (lines 40-45).

**C.6 — SelfTrafficRegistry TOCTOU. (correct)**
Registration happens after `Bind`, before SYN/send (`onSocketReady`, `Socks5ControlConnection.cs:122-123`; the UDP relay registers after bind before first send, `Socks5UdpTransport.cs:153-162`) — the §10 race is closed. Stale-token `Remove` is generation-guarded (`SelfTrafficRegistry.cs:38-48`). Shutdown is ordered: the capture loop stops before mode restoration and coordinator cleanup (`CaptureLifecycle.cs:145-156`), so the registry never outlives the pumps. Remaining (intentional) gap: `IsOwned` pays the full lock even when the registry is empty — pure performance (B.2.2).

**C.7 — IdleExpirySweeper. (mostly correct)**
The TCP→flows ordering is correct with recorded rationale (`IdleExpirySweeper.cs:66-75`); per-tick failures are isolated and rate-limit logged (lines 89-94, S6d). `IdleExpirySweeperFailureTests.cs` covers: UDP `RemoveExpiredAsync` repeated failure → loop survives, exactly one warning per 5s window. **Not covered / residual**: (a) intra-tick ordering — a throwing TCP sweep also skips that tick's flows and UDP sweeps (next tick retries; benign, untested); (b) flow expiry does not hold UDP sessions in `isHeld` (only `_tcp.HoldsFlow`, line 74) — active UDP flow decisions expire after 5 min and the next datagram re-claims a new generation; with today's fixed policy the decision is identical, so benign, but a live policy swap could reclassify active UDP sessions — worth adding the UDP side to `isHeld` or a comment. (c) The first sweep comes after a full interval; short-lived bursts are bounded only by capacity (65536) — fine.

**C.8 — Socks5ControlConnection protocol robustness. (strong)**
Discriminating parse (L2, `Socks5State.cs:66-92`): invalid version, status >8, RSV≠0, wrong ATYP, zero domain length, truncated success body are all rejected; prefix validation is separate (lines 156-162), so the 5B read does not over-apply full-reply rules. A truncated stream → `ReadExactlyAsync` throws. Per-stage timeouts derive from the held per-attempt CTS (`Socks5ControlConnection.cs:125-127, 214-247`) — the command-stage scope is intentional and documented; the `CancelAfter` armed at 30s is inert for an idle relay because `GetUpstreamStream` clears socket timeouts (lines 209-211) and the relay code never consumes the `AttemptToken` (CTS + timer stay alive until dispose — trivial). Sockets are correctly disposed on every failure path via `DisposeFailedAttemptAsync` (lines 337-348) with ownership-transfer guards (lines 129-132). 0xFF method reply and auth failure close with `IOException`; `IsFatal` semantics distinguish socket-list exhaustion from real errors (lines 79-82). Domain-reply DNS is bounded under `cancellationToken` (lines 307-311). No robustness holes found; the only sharp lever is the 150s worst-case budget (B.4).

**C.9 — ABI safety. (strong)** Sizes/offsets asserted at driver open (`NdisApiAbi.cs:23-56`); `GetFrame` clamps length to 1514 (`NdisPacketBuffer.cs:74`); driver `PacketsSuccess` clamped; adapter counts clamped. `TcpAdapterList` (8.8KB) is stack-resident under the control gate — within a 1MB stack budget, cold per process.
