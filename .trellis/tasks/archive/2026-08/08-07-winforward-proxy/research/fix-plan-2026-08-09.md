# WinForward Fix Plan (2026-08-09)

Review source: `review-capture-lifecycle-config-2026.md` + protocol subagent report + main-session deep review
of the capture/proxy data path. This document lists each confirmed bug, the exact fix, affected files,
and the test to add. All fixes are scoped and do not change the public config contract or PINed ABI.

Severity key: H=high (clear functional damage), M=medium (specific scenario), L=low (robustness/diagnostics).

---

## H1 — UDP traffic dropped when a local/remote port numerically collides with an active TCP proxy-listener port

### Problem
`FlowDispatcher.DispatchAsync` invokes the TCP reverse handler (`_reverseHandler`
= `TcpProxyCoordinator.HandleReverseIfApplicableAsync`) on **every** non-self-traffic packet, including
UDP and non-flow frames. `HandleReverseIfApplicableAsync` → `TcpRedirectTable.TryResolveByProxyPort`
matches **by numeric port alone, with no protocol check**. A UDP datagram whose source or destination
numeric port equals an active TCP listen port → `HandleReverseAsync` runs → `TryRewriteTcpEndpoints`
fails for UDP (protocol byte != 6) → returns `TcpRedirectOutcome.Blocked` → the dispatcher completes
the packet with `Block`, **silently dropping an unrelated UDP datagram**.

### Fix
Gate the reverse handler on TCP only, at the earliest point (the dispatcher), so no cross-protocol
misclassification is possible:
- `src/WinForward.Runtime/FlowDispatcher.cs`, in `DispatchAsync`, before invoking `_reverseHandler`,
  early-return/skip it when `packet.Context.Key.Protocol != TransportProtocol.Tcp`.
- Belt-and-suspenders: in `TcpProxyCoordinator.HandleReverseIfApplicableAsync`, return
  `TcpRedirectOutcome.NotRelevant` immediately when `key.Protocol != TransportProtocol.Tcp`.

### Test
- `FlowDispatcherTests`: a UDP flow (or a non-flow UDP frame) whose local AND remote ports equal a
  registered TCP proxy-listener port must still be evaluated by normal flow/policy and NOT be dropped
  by the reverse handler — i.e. the reverse handler neither returns Injected nor Blocked for UDP.
- `TcpProxyCoordinatorTests`: `HandleReverseIfApplicableAsync` returns `NotRelevant` for UDP.

## H2 — UDP response reinjection for Forwarded (Hyper-V/VM) flows targets the host adapter/MAC instead of the origin adapter

### Problem
`UdpResponseReinjector` is constructed once with `scope[0]` (host adapter) handle and the host MAC,
and uses that same adapter + MAC for **both** Host and Forwarded origin UDP responses
(`_reinjector.SendToAdapter(_adapterHandle, …)` for Forwarded). Hyper-V forwarded UDP replies are
therefore sent out the host adapter and cannot reach the VM. The TCP path already chooses
toward-MSTCP vs toward-origin-adapter from the stored origin; UDP does not carry the origin adapter.

### Fix
Give the UDP sink the ability to target the correct adapter per flow:
1. Change `IUdpResponseSink.InjectAsync` to accept an `AdapterContext`/target adapter handle (and the
   flow's saved origin adapter identity) so `UdpResponseReinjector` can resolve the correct handle + MAC.
   - Simplest correct scope for release 1: capture the flow's origin adapter identity in
     `UdpProxySession`/`UdpProxyCoordinator` and pass it through.
2. `UdpResponseReinjector` should maintain a map of origin-adapter `(handle, MAC)` resolved from the
   adapter inventory; for a Host flow use the host adapter (handle + MAC as today); for a Forwarded
   flow use the origin adapter's handle and the VM-facing MAC.
3. If the origin adapter cannot be resolved at inject time, fail closed (drop the response) with a
   rate-limited structured log, rather than silently sending it out the wrong adapter.
4. Also correct the direction flag (see H3) so Forwarded adapter injection carries the right
   `PacketFlagOnSend`.

Where the origin adapter identity cannot be plumbed cleanly in release 1 (e.g. `UdpResponseSink`
interface change ripples into `UdpProxySession`), prefer a thin, explicit seam: pass the flow's
origin `AdapterContext` into `Sink.InjectAsync`. This is the single seam; no policy changes.

### Test
- `UdpRelayTests` / hardware-agnostic seam test: a Forwarded-origin UDP flow's response is routed
  toward the origin adapter handle (via a recording `IPacketReinjector`/sink fake) and built with the
  origin adapter's MAC, while a Host-origin flow still routes to MSTCP.
- If the origin adapter is missing/unresolvable, the response is dropped fail-closed (no throw into
  the receive loop) and logged.

## H3 — Forwarded-direction injection uses the wrong direction flag

### Problem
Per the project's documented pass/revert matrix (design §1, research constraints), a frame injected
toward an adapter is an `ON_SEND`; `ON_RECEIVE` is interface→MSTCP. `TcpRedirectInjector.InjectAsync`
hard-codes `PacketFlagOnReceive` regardless of `towardMstcp`, and `UdpResponseReinjector` does the
same for the Forwarded `SendToAdapter` branch. The Host-flow path happens to be correct (injects
toward MSTCP = ON_RECEIVE), but the untested Hyper-V forwarded direction uses the wrong flag.

### Fix
- `src/WinForward.Runtime/TcpRedirectInjector.cs`: set device flags = `towardMstcp ? PacketFlagOnReceive
  : PacketFlagOnSend` before `SetFrame`.
- `src/WinForward.Runtime/UdpResponseReinjector.cs` (Forwarded branch inside `InjectAsync`): when
  routing to the origin adapter use `PacketFlagOnSend`; Host→MSTCP keeps `PacketFlagOnReceive`.

### Test
- `TcpRedirectInjector`/`UdpResponseReinjector` unit test asserting the buffer's `DeviceFlags` value
  matches the injection direction (Host→MSTCP = ON_RECEIVE, Forwarded→adapter = ON_SEND).

## M1 — UDP ASSOCIATE: BND.ADDR `0.0.0.0`/`::` substituted with the TCP control peer; `::ffff:` not handled

### Problem
`Socks5Client.ReadEndpointReplyAsync`: when the reply BND address is `0.0.0.0`/`::`, it substitutes
`socket.RemoteEndPoint.Address` (the TCP control peer) without re-validating the port, and does not
handle IPv4-mapped `::ffff:a.b.c.d`. On multi-homed servers where the UDP relay lives on a different
interface/IP than the TCP control connection, UDP proxy fails closed / mis-targets.

### Fix
Apply the loopback/unspecified substitution **only for the UDP ASSOCIATE relay binding** and only when
the reply truly is an unspecified wildcard, then map IPv4-mapped addresses to their IPv4 form:
- Keep the `Any`/`IPv6Any` substitution to `socket.RemoteEndPoint.Address` (this is the RFC-endorsed
  fallback for UDP ASSOCIATE returning 0.0.0.0), but:
  - Normalize an IPv4-mapped `::ffff:x.y.z.w` reply address to its IPv4 `IPAddress` before deciding.
  - After substitution, keep the server-provided BND port (do not override it with the TCP port).
- Do NOT apply any address substitution to `CONNECT` replies (their BND.ADDR is not used for routing;
  the current scope only consumes CONNECT replies for success/validation, so leave them unrouted).

### Test
- `Socks5StateTests`/`Socks5ClientTests`: reply with `::ffff:0.0.0.0`/`0000::` maps to the control
  peer; the returned port is the reply port; a CONNECT reply with `::ffff:` is not mistaken for a
  relay route.

## M2 — IPv6 link-local ScopeId dropped in SOCKS5 reply + UDP relay address parsing

### Problem
`Socks5Client.cs` (`new IPAddress(reply.AsSpan(…))`) and `Socks5Udp.TryReadAddress` (`new IPAddress(bytes)`)
build IPv6 addresses with `ScopeId == 0`, while other code deliberately preserves scope. Link-local
(`fe80::`) SOCKS servers/relays cannot be addressed.

### Fix
- Preserve scope by parsing via `IPAddress.Parse`/`new IPAddress(byte[], long scopeId)` where the
  scope is available, or route relay addressing through the resolved endpoint that already carries a
  scope. In the first release the transparent-interception destination IP is already-resolved, so the
  practical exposure is narrow; the fix is to stop rebuilding the address such that scope is lost and,
  where the parser accepts only raw bytes, carry the scope from the SOCKS reply/control endpoint.
- Note: packet-path flow keys carry `Endpoint.Address`; keep parity with `IpPrefix`/`ProcessAttribution`
  scope handling so a link-local relay endpoint resolves on the correct interface.

### Test
- A link-local `fe80::` relay/control endpoint preserves a non-zero `ScopeId` through
  `Socks5UdpCodec`/`Socks5Client` address reconstruction (pure test with a fake reply).

## M3 — UDP frame size cap hard-coded to 1514 while the NDISAPI ABI may be jumbo (9014)

### Problem
`UdpFrameBuilder.MaximumEthernetFrame = 1514`. If the pinned `ndisapi.dll` is a `JUMBO_FRAME_SUPPORTED`
build (INTERMEDIATE_BUFFER up to 9014), unfragmented UDP payloads >1514 supported by the driver are
silently dropped at `TryBuild`. The constant must reflect the pinned native ABI, not a magic number.

### Fix
- Expose the frame cap as a configurable/ADU-injectable constant defaulting to 1514 (matching the
  non-jumbo pinned ABI used for the release), and allow the runtime to pass the actual NDISAPI
  `MAX_ETHER_FRAME` (1514 vs 9014) from `NdisApiAbi`. `UdpResponseReinjector`/`UdpProxyCoordinator`
  thread the cap through.
- Keep fail-closed behavior for frames that exceed the pinned cap; only raise the cap when the pinned
  ABI actually supports jumbo.

### Test
- `UdpFrameBuilder` accepts a payload of `cap - 8 - ethernet/ip/udp overhead` and rejects `cap + 1`
  for both 1514 and 9014 caps, and `UdpResponseReinjector` honors the configured cap (recording sink).

## M4 — TCP idle expiry tears down long-idle-but-established connections

### Problem
`IdleExpirySweeper` sweeps `TcpProxyCoordinator.RemoveExpiredAsync(now, redirectIdleTimeout=5m)`, but a
redirect association's `LastActivityUtc` is only touched by re-captured packets on the proxy leg. A
live TCP connection that is silent at the packet level for >5 min (e.g. SSH without keepalive) is
force-torn-down (listener+relay+token), severing an otherwise healthy connection.

### Fix
Distinguish "no packets observed" from "flow is not making progress". Most correct and smallest change:
- Do not expire a session whose relay is **actively Relaying**; only expire sessions still in
  `RelayPhase.Redirecting` (half-open, never completed setup) — these are genuinely abandoned.
- During `Relaying`, tie teardown to the relay socket failing/ending (already handled via
  `ObserveRelayCompletionAsync`), not to a wall-clock idle timeout. If a bounded idle reclaim of
  relaying sessions is still desired, gate it behind a much longer, documented timeout and add socket
  read/write timeouts in `TcpProxyRelay.PumpAsync` so a stalled relay cannot hold the slot forever.

### Test
- `TcpProxyCoordinatorTests`: a session whose phase is `Relaying` (relay live) is NOT removed by
  `RemoveExpiredAsync` past the idle timeout; a session stuck in `Redirecting` (never relayed) is.
- Keep UDP idle expiry unchanged.

## M5 — `_byProxyPort` reverse index has no protocol/address-family/generation constraint

### Problem
`TcpRedirectTable.TryResolveByProxyPort` matches on numeric port alone. Under concurrency (16K TCP
sessions across half the ephemeral range), reverse-packet disambiguation by port alone is fragile and
amplifies H1. The listen port is unique per flow, but the *observed* reverse frame's source/dest port
is the listen port; the table can only key on that port value.

### Fix
Row H1 fixes the cross-protocol case. For the TCP-only residual: scope the H1 gate + add an
`AddressFamily` check in `TryResolveByProxyPort` call sites so an IPv6 reverse frame can't match an
IPv4 flow's port index (and vice-versa). Add protocol==Tcp assertion as a code-level guard in
`HandleReverseAsync`. (Adapter/generation scoping is out of scope for release 1; document as known.)

### Test
- `TcpProxyCoordinatorTests`: an IPv6 frame with a port matching an IPv4-only association returns
  `NotRelevant` (not routed into reverse handling).

## L1 — SOCKS5 ConnectAsync: no total deadline across组成 resolution + sequential connect attempts

### Fix
Bound `Socks5ControlConnection.ConnectAsync` with `cancellationToken` already (it is cancellable); add
a per-connect-attempt socket `ReceiveTimeout`/`SendTimeout` and a global attempt cap/timeout, logging a
redacted diagnostic. Keeps fail-closed (exception → blocked) without changing policy.

## L2 — `TryParseReply` returns success early for failure REP 1-8 with <4-byte bodies

### Fix
Make `TryParseReply` return a discriminated result that reports a well-formed success reply vs. a
definite failure status; never `return true` on an undersized reply without the caller verifying
`status`. Keep current caller safe (it already short-circuits on `status != 0`), but harden the API
and add a test that a truncated failure reply is rejected, not parsed into garbage.

## L3 — `DrainRedundantConnectionsAsync` blanket `catch { continue; }` can spin on non-cancel/non-disposed accept errors

### Fix
Filter the accept loop to break on `OperationCanceledException`/`ObjectDisposedException`; for other
transient accept errors, rethrow after a bounded delay rather than busy-looping `continue`.

## L4 — Self-traffic registration for the TCP listener leg is effectively a no-op

### Problem
`CompleteNewRedirectAsync` registers `SelfTrafficKey(Tcp, Any:lp → Any:lp)`, which matches no real frame;
the listener/reverse leg is secured only by the reverse hook.

### Fix
With H1's TCP-only gate in place the reverse hook is the correct guard for the listener leg. Update the
registration intent/comments to state this explicitly, and register the exact wildcard form that the
`SelfTrafficRegistry` wildcard matcher can actually match (`Any:localPort → originalServer:port` is
not expressible before CONNECT; document that reverse handling, not the registry, protects the leg).
No code change strictly required beyond clarity; ship H1.

## Validation & refinements (2026-08-10, main-session + research/check subagents)
1. H1 confirmed: non-flow frames already bypass the reverse hook (`DispatchNonFlowAsync` does not call it); only
   `DispatchAsync` does. So gating on `Key.Protocol == Tcp` in `DispatchAsync` before `_reverseHandler` is correct and
   sufficient; no need to touch non-flow. Add the belt-and-suspenders protocol guard in
   `HandleReverseIfApplicableAsync`. Adopt M5's AddressFamily check in the reverse path (an IPv6 frame with a port
   colliding with an IPv4 flow's listen port is the same drop class — fold protocol+family into one early gate).
2. M4 MUST add socket timeouts as part of the fix, not as an option: if Relaying sessions are exempted from the idle
   sweeper, a stalled relay (peer stopped reading/writing) would otherwise live forever because `TcpProxyRelay.PumpAsync`
   uses `CancellationToken.None` and never times out, so `Completion` never resolves. Add per-direction read/write
   timeouts (or a socket Send/Receive timeout) so a dead relay ends and is reclaimed by `ObserveRelayCompletionAsync`.
3. H2 concrete seam (replaces the vague "inventory" wording): `UdpResponseReinjector` takes an injectable
   `IReadOnlyDictionary<string, (nint Handle, byte[] Mac)>` keyed by adapter StableId (plus the host entry). It resolves
   `originalFlow.OriginAdapterId`; Host flows use the host entry (as today); Forwarded flows use the origin entry; if the
   origin adapter is not in the map, fail-closed drop the response with a rate-limited log instead of sending it out the
   host adapter. Map is fake-constructed in tests (no NDISAPI).
4. M1: extract a pure `Socks5Messages.NormalizeBndAddress(replyAddress, controlPeer, command)` so the substitution + IPv4-
   mapped handling + port-preservation are hardware-independent unit-testable.
5. L1: extract the connect-attempt loop behind a `Func<IPEndPoint, Socket>` socket factory + an address-list provider, so
   the attempt cap/deadline/socket-disposal are testable with fakes; fail-closed to blocked.
6. M3: `UdpFrameBuilder.TryBuild`/cap is threaded as a parameter (default 1514) through `UdpResponseReinjector`; host
   passes the actual NDISAPI `MAX_ETHER_FRAME` (1514 vs 9014) from `NdisApiAbi`. Keep fail-closed at the configured cap.
7. Native-AOT: all seams are plain interfaces/records/Funcs; no reflection/dynamic type usage added. `IUdpResponseSink`
   signature change must update `UdpProxySession`/`UdpProxyCoordinator` call sites; keep it minimal (add an adapter
   context parameter).
Overall plan verdict: APPROVED with the above refinements folded in.
